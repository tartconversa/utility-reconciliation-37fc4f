# 分析产品方法说明

本文件说明 `attribution/` 分析包如何把资料口径变成可重现的评审结论。所有主体和观测
仍是本地合成资料；方法本身面向真实资料设计。

## 1. 要回答的问题

压缩机汽改电的设备侧减汽可以计量，但少用的蒸汽在全厂公用工程边界内有两种完全不同的
去向：让锅炉少烧煤，还是只让背压汽量减少、外购电增加。把“减汽 × 固定单价”直接记为
节约，会在后者发生时报出厂区并不存在的收益。本产品只回答**全厂边界**的能源、费用和
排放变化，并对识别不出的部分保留结论范围。

## 2. 资料口径的实现方式

| 口径要求（docs/资料口径.md） | 实现位置 |
| --- | --- |
| 4 小时 value 是实际 4 小时总量，不再乘除 | `dataio._build_daily` 同窗直接求和，并校验每日覆盖 8 小时 |
| bound 对每条观测生效，不是标准差 | 同日多条分表的界相加为日窗界（`meter_daily_bounds`） |
| 未计量边只有容量、无已知流量，禁止隐含平衡插件 | LP 中 `mp_vent/lp_loss/waste_mp` 只给容量域，目标不含反推项 |
| 可信测量不得任意修改 | 计量边流量限定在观测±日窗界内，越界只能进显式节点松弛 |
| 设备消耗不能凭空变成 LP 供汽 | 网络只有 `hp_device` 一条设备用汽边，无设备到 LP 的连接 |
| 背压发电按 hp_mp 汽量计 | `network.backpressure_generation` 与 eval 的电力结算 |
| 供汽缺口不可用购电替代 | LP 平衡不含电力替代变量，相同服务量下 `lp_user` 域不变 |
| 不提供预定节煤模型 | `models.fit_coal_model` 只做受控估计，识别不出即报不可识别 |
| 证据可知时间 | `dataio.load_pack(as_of=...)` 按 `available_at` 切片并计数排除项 |

## 3. 分析流程

```
load_pack(as_of)                只读载入 + 证据时点切片 + 多间隔日窗对齐
  ├─ balance.balance_pack       逐日 LP 可行平衡、冲突诊断、未计量流量可行区间
  ├─ models                     煤-汽受控回归、电力边界检验、负荷档匹配
  ├─ eval.run_review            基线 + 单项/组合反事实 LP、能源费用排放区间、联合交互
  ├─ sensitivity                排序稳健性、误差收紧、测量/价格来源分解、决策证据状态
  └─ verify                     改造后承诺检验与证据时间线
```

### 3.1 可比工况

基线只取**改造前且非检修**的 28 个日窗。改造前后负荷同为 0.55–0.85 七档循环、服务量
分布一致（同为 110–134 t），因此同负荷档的对照是有资料支持的可比条件。检修日不剔除
原始观测，但不进入反事实基线；报告保留其标记。

### 3.2 可行平衡与冲突

每个日窗解一个线性规划：计量边在观测±界内取值，未计量边在物理容量内取值，三个压力
节点（HP/MP/LP）要求平衡，仅当误差界内无解时才允许高惩罚的节点松弛。

- 60 个日窗中 **11 天** HP 节点存在仪表误差无法解释的不平衡（手工残差核算与 LP 松弛
  完全一致，最大松弛 4.0 t），MP/LP 节点全部可行。
- `lp_loss` 逐日可行区间始终落在登记容量 [0,12] t 内，未被用于自动凑平衡。
- `mp_vent` 与 `waste_mp` 联合不可识别：无补测日只能给二者组合区间；2025-02-15/16 的
  补测在 2025-03-09 可知后，把这两天的放空区间从宽度约 19 t 收紧到 2 t。

### 3.3 煤耗关系的可识别性

煤耗呈严格的星期内锯齿（周一 8.00 起每日 +0.29 t，周末重置）并在改造阶段整体下移
0.30 t/日。控制星期效应与改造阶段后：

- 锅炉汽量对煤耗的偏系数 = 0.0000，加入该变量 ΔR² = 0；
- 同期锅炉出力改造前后无实质变化（负荷档匹配差 < 1 t）。

因此资料**不支持任何节煤模型**：改造阶段的 -0.30 t/日煤耗差不能归因于减汽。所有方案
的煤项记 0 并标注 `not_identifiable`，观测煤耗差只作为未归因对照，不进项目收益。
未控制星期的双变量回归（R²≈0.71）被保留为伪相关对照，明确禁止用于归因。

### 3.4 反事实评估与联合归因

方案的设备侧假设（减汽、增电、余热变化）只作为 `hp_device` 目标中心、`device_kwh`
和余热容量的反事实输入；全厂购能由网络重新平衡后逐边求 min/max 区间。

本资料下三方案的共同结论：减汽在测量界内主要经 **HP→MP 背压通道**吸收，锅炉出力
区间不缩小，背压发电区间变化不足以抵消设备增电，购电净增、费用净增。

- 部分基线日窗在叠加减汽后超出仪表误差的可平衡能力（方案 A 13 天、B 3 天、AB 27 天，
  松弛全部在 HP 节点）。这些“反事实不可平衡日”显式计数，不被静默平衡；收紧 M1/M2/M4
  误差界会暴露更多不相容，同时收窄费用区间。
- 组合 AB 与 A+B 的交互区间**包含 0**：现有测量无法证明余热交互，单项加总与组合结果
  不相悖，但也不能声称可加。判定逻辑（区间含/不含 0）在 `eval._interaction_terms`。

### 3.5 外部情景与来源分解

物理反事实（汽、电、煤区间）不随 `external.csv` 变化；情景切换只改变线性价格与排放
因子。`decompose` 命令把情景间差异显式标注为“外部价格/排放因子”来源，与测量改进
（`tighten` 命令）区分，评审依据可按同一 as_of 重现。

## 4. 本资料下的评审结论（central 情景，每日均值）

| 方案 | 购电增量 kWh | 费用增量 元 | 排放增量 kg | 节煤 | 排序 |
| --- | --- | --- | --- | --- | --- |
| B | [1014, 1289] | [710, 902] | [588, 748] | 不可识别，记 0 | 1（区间不重叠，稳健） |
| A | [1514, 1732] | [1060, 1213] | [878, 1005] | 不可识别，记 0 | 2（稳健） |
| AB | [2714, 3021]→[2714,2899] | [1900, 2029] | [1574, 1681] | 不可识别，记 0 | 3（稳健） |

实际实施的改造对应方案 A：负荷档匹配实测减汽 7.92 t（承诺 8，仪表界内容忍），
实测设备增电 1800 kWh（承诺 1700，power 表无误差界，按点值判定偏离），购电净增
约 1790 kWh——减汽未减少锅炉出力，增电几乎全额变为外购电。

**投资含义**：在当前测量与煤-汽关系下，三个方案都不产生可计量的净节约；B 的增量
代价最小。要让“节煤收益”进入决策，需要补测分炉煤耗与锅炉煤-汽关系；要量化组合的
余热交互，需要连续的放空/回收计量（现有仅 2 天补测）。

## 5. 已知资料问题

`data/catalog.json` 登记的 8 个 sha256 与实际 CSV 全部不符（行数、字段一致，疑为
登记摘要在文件最终化前生成）。`python -m sourcepack` 与原 `test_pack` 因此失败；
分析包以原始 CSV 为唯一数据来源，`checksum` 命令显式披露该不一致，不静默通过。
修复方式是用当前文件重新生成 catalog 摘要，但这属于资料治理动作，未自动执行。

## 6. 命令清单

```
python -I attribution/__main__.py --root <资料根> checksum
... balance   [--as-of TS] [--out f.csv]      逐日平衡与冲突
... review    [--scenario central|low_grid|peak_price] [--as-of TS] [--out f.csv]
... verify    [--proposal A] [--timeline]     承诺检验与证据时间线
... scenarios [--out f.csv]                    价格/排放情景对比
... rank      [--metric delta_cost_yuan|delta_emission_kg|delta_import_kwh]
... decision                                   逐项证据状态（supported/range_only/needs_measure）
... tighten   --bound edge_id=单读数界 ...     误差收紧重评（可重复指定）
... decompose                                  测量 vs 外部价格来源分解
```

隔离模式（`-I`）下 cwd 与 PYTHONPATH 不生效，故用脚本路径调用；普通环境也可用
`PYTHONPATH=<根> python -m attribution ...`。
